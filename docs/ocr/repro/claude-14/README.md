# 小地圖點大小讀尺寸：機器人 v3 與 claude-14（v2.13 與最新版 v2.22）

2026-11-25（台灣時間）。分支 `ocr-claude`，接續 [claude-13](../claude-13/README.md)（d15dc70）。依使用者決定，維持原目標，只測 v2.13 與 v2.22。全部為新檔案，或只改本分支新增的檔案。不是 OCR4 驗收。

## 結論

- **小地圖的點大小帶有 NPC 尺寸資訊**：遊戲畫的點半徑是 `clamp(r/38,1.2,3)`，所以半徑 45.6～114 的 NPC 可以從點的大小讀出尺寸。
- **受限全知機器人 v3**（v2 加上點大小資訊）在 **v2.13 達到 4/12（33%）**、0 死亡；v2 只有 1/12。v2.22 是 3/12（25%）、1 死亡，和 v2 相同。這是目前只用畫面資訊的最佳結果。
- **控制器 claude-14**（claude-12 加上點大小讀取）：0/24 過關。v2.13 體型中位約 72、1 死；v2.22 中位約 80、3 死。比 claude-11 差。
- **控制器和機器人的差距**：主要是吞 NPC 的次數，機器人約為控制器的 2 倍（v2.13 是 21 對 11，v2.22 是 17 對 10.5）。獵物大小比例（約 0.56～0.66）和移動速度都差不多。

## 點大小讀取（`whiteDots` 的 `rEst`）

- 覆蓋量總和 mass 約等於 π·rad²·q²，所以 rad=√(mass/π)/q；rad≤1.32 視為未知，≥2.9 視為 114，其餘 r=38·rad。
- 色塊邊界框比單一圓點應有的大小（2·rad·q+2.2）還大時，視為多個點黏在一起，尺寸改回未知。合成檢查有對應項目。
- **實測**（`scripts/probe-dotsize-ocr-claude.mjs`，claude-14 各 1 局，130 秒）：

| | 讀到尺寸的樣本 | 讀出值／真實值 中位（p10～p90） | 讀出 ≥46 但真實 <40 |
|---|---|---|---|
| v2.13 | 1166 | 0.97（0.91～1.00） | 83 |
| v2.22 | 410 | 0.97（0.92～1.02） | 67 |

- 「讀出 ≥46 但真實 <40」可能有一部分是探測腳本的配對窗口（160px）配到附近的小 NPC。
- **claude-14 的用法**：畫面外白點如果讀到尺寸，≥1.06R 的改當成致命（靜態）；其餘用讀到的尺寸當獵物。讀不到的，用 min(0.6R, 45)。

## 差距分析（決策比對，claude-14）

- **假危險**很少：控制器以為間距 <60、但真實最佳方向間距 ≥160 的，v2.13 只有 7 次、v2.22 有 28 次。
- **「真實狀態下 1.5 秒內可吃到獵物，控制器卻選了別的方向」**，v2.13 有 353 次、v2.22 有 320 次：
  - **A. 控制器看到了獵物，但方向偏了**（v2.13 有 261 次、v2.22 有 172 次）：常見的是偏 45°，例如西南對西、東北對北。原因待查，可能是獵物位置或速度的預測誤差，或 8 方向的量化。
  - **B. 獵物在畫面內，控制器卻沒看到**（v2.13 有 92 次、v2.22 有 148 次）：控制器這時轉去追畫面外的白點。
- **辨識量測**：致命看成安全 v2.13 1/448、v2.22 0/505；誤判為獵物 1.3%／0%。

## 測試條件

- Linux 6.18（雲端），Chrome for Testing 153.0.8010.12 headless，Playwright 1.63.0，Node 22.23.5，視窗 2000×1163，DPR1，視野「標準」。
- 本輪開始前雲端環境重新啟動過，所有批次都在重啟後才開始。
- 每次兩批同時跑，順序固定，不補跑、不刪除，無 seed。合成檢查 67 項。

## 下一步

1. **A 類（方向偏了）**：比對控制器對獵物的預測（位置、速度）和真實值，判斷是預測誤差還是決策計分的問題。
2. **B 類（漏看）**：查出畫面內獵物沒被偵測到的原因，例如和食物或其他 NPC 黏在一起，或位在 UI 遮罩區。
3. 這兩類補上之後，控制器才有機會接近機器人 v3 的成績（v2.13 33%、v2.22 25%）。要達到每版 50%，機器人本身的決策也還要再改進。
